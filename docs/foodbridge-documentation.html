1. Product overview

FoodBridge is a multi-role web application that rescues surplus food from restaurants, bakeries and supermarkets and routes it to verified low-income families through volunteer drivers. It is a working application with authentication, role-based dashboards, a relational database, file storage and automated notifications — not a marketing landing page.

Problem addressed

SDG 1 — No Poverty. Food is the largest flexible expense for low-income households. Reliable food support releases money for rent, transport, school and medical costs.
SDG 2 — Zero Hunger. Roughly one third of food produced is wasted while families go without. Redirecting safe surplus closes the gap without producing anything new.

4. Role dashboards

All four dashboards share one shell: a fixed 264 px sidebar (drawer below 1024 px), a sticky top bar with page title, notification bell and profile menu, and a content area on #F6F8F7.

4.1 Donor — /donor

  • Overview — total donations, live listings, items awaiting review, meals contributed, five most recent listings.
  • My donations — searchable table with status badges, inline edit modal and delete confirmation.
  • Add donation — food name, category, quantity and unit, expiry date, city, pickup address, description, and a drag-and-drop photo upload (JPEG/PNG/WebP, 5 MB) written to Supabase Storage. New listings enter pending.
  • Incoming requests — every match on the donor’s food with the matched quantity, family size, fit score and delivery status.

4.2 Beneficiary — /beneficiary

  • Overview — request counts and food received, with a verification banner while the account is pending.
  • Browse food — filtered catalogue with a “Request this food” dialog that pre-fills category and a sensible quantity, validated against availability.
  • My requests — status tracking, rejection reasons, cancellation of pending or approved requests.
  • New request — category, quantity, household size, urgency, area and situation notes.

4.3 Volunteer — /volunteer

  • Overview — availability toggle (available / busy), active tasks, completed count, open unassigned tasks, capacity and transport.
  • Delivery tasks — accept any open task, then progress it assigned → picked_up → in_transit → delivered. Final step cascades the whole chain (see §8).
  • History — completed and cancelled deliveries with timestamps.

4.4 Administrator — /admin

  • Overview — registered users by role, donations, meals, deliveries, and four work queues (verifications, donation reviews, request reviews, unmatched approved requests) plus recent activity.
  • Users — searchable, role-filtered table; verify or suspend accounts; full profile drawer including verification evidence.
  • Donations — moderation queue by status; approve (optionally with an internal note) or reject with a reason that reaches the donor.
  • Requests — approve, reject with a reason, review family context.
  • Smart matching — see §5.
  • Deliveries — assign or reassign volunteers, monitor live status, force-complete a handover.
  • Analytics — platform KPIs, trend chart, category performance, operational health bars, CSV export.

5. Smart matching engine

Matching is deterministic application logic implemented in src/lib/matching.ts. No AI model, no external API. A request is compared with every approved donation and scored out of 100.

CriterionWeightRule
Category fit40Exact category match = 40; request accepts “any food” = 20; mismatch = 0.
Quantity20Donation covers the request = 20; covers at least half = 12; otherwise 4.
Expiry urgency15Expires within 3 days = 15 (rescue priority); within 7 days = 10; later = 5; expired = 0.
Location15Same city = 15; different city = 5; unknown = 3.
Request urgency10critical 10 · high 7 · normal 4 · low 2 — this is what pushes urgent families to the top.

The UI shows the score plus a per-criterion breakdown bar, and the reasons behind each decision, so an administrator can see why a pairing was proposed rather than trusting a black box.

score = min(100, category + quantity + expiry + location + urgency)

Example — "Family Produce Mix" (produce, 40 servings, +3 days, Tampines)
matched to Fatima (produce, 15 servings, critical, Tampines):
  category  40  (exact match)
  quantity  20  (40 >= 15)
  expiry    15  (<= 3 days)
  location  15  (same city)
  urgency   10  (critical)
  ─────────────
  total     100 / 100

Workflow: administrator selects an approved request → reviews ranked candidates → Create match (status proposed) → Confirm (donation and request become matched) → Assign volunteer (creates the delivery and notifies the driver).

Eight tables in the public schema of a PostgreSQL database, all with foreign keys and constraints. Identity is owned by Supabase Auth; public.profiles mirrors each account.

7. Security and row-level security

Every table has RLS enabled and a role-specific policy. Anonymous visitors can read only approved donations, through a column-restricted grant that excludes donor_id.

TableAccess rule
profilesOwn row or administrator. Insert restricted to a self-owned row with role ≠ admin.
donationsApproved rows are public; owner and administrator see everything; matched families and assigned volunteers see the listing they are involved in.
assistance_requestsOwn requests, the donor of a matched donation, the assigned volunteer, or administrator.
matchesVisible to the donor, beneficiary and volunteer involved, plus administrator. Writes are administrator-only.
volunteersOwn record or administrator.
deliveriesInvolved parties or administrator; unassigned tasks are visible to any active volunteer so they can be claimed.
notificationsOwn rows only; no client inserts.
reviewsReviewer or reviewed party (and administrator); one review per pair, self-reviews blocked.
Privilege-escalation defences. Owners cannot change their own role, status, verified_at or email. A donor cannot approve their own donation; a beneficiary cannot approve their own request; both are silently reverted by guard triggers. Volunteers may only progress the status of their own assignment and cannot reassign it. Helper predicates (is_admin, can_view_donation, can_view_request, can_view_match, can_view_delivery) are SECURITY DEFINER with a pinned search path, which also prevents policy recursion.

Passwords are handled entirely by Supabase Auth and stored as bcrypt hashes in auth.users; no plaintext or password hash exists in the application schema or the client bundle.

8. Notifications and automation

Notifications are generated by database triggers, not by the browser, so they cannot be forged or missed when a request fails mid-flight.

EventRecipient and message
Donation approved / rejectedDonor — approval confirmation, or rejection with the administrator’s reason.
Request approved / rejected / fulfilledBeneficiary — status change with any review note.
Match createdBeneficiary (“a matching donation was found”) and donor (“being scheduled for pickup”).
Delivery createdVolunteer — new assignment with the pickup address.
Delivery marked deliveredDonor, beneficiary and volunteer; also cascades match → completed, donation → completed, request → fulfilled.

The bell in the dashboard top bar polls the unread count, and /notifications lists everything with per-item and bulk “mark read”.

Data access is centralised in src/lib/api.ts: one typed function per query, with errors normalised into readable messages. Components never build queries inline except for the two composite reads (donor request view, delivery claim).

Charts are hand-authored SVG components (area trend, bar, donut, progress) — no charting dependency, so the bundle stays small and the styling follows the token system exactly.

Feedback uses a toast provider for transient results, inline field errors for validation, skeleton/spinner states for loads and explicit empty states for every list.

10. Internationalisation (EN/AR)

The interface ships in English and Arabic. The choice is made in Settings → Language & region or from the switch in the site header, and is persisted per browser.

  • Full RTL mirroring — dir="rtl" on the document, logical CSS properties (ps-*, start-*, border-e) so the sidebar, tables and cards flip without duplicate styles.
  • Localised data labels — food categories, months, dates and relative times (for example "3 days ago" rendered in Arabic) follow the active language.
  • Shared links — ?lang=ar or ?lang=en opens the app in that language.
  • Consistency rule — when Arabic is selected, no English UI string remains; dictionary lookups fall back to English only for a missing key, never mixing text on screen.
User-authored content (food names, notes, organisation names) is stored and displayed exactly as entered — translation applies to the platform interface only.

11. Configuration and deployment

Environment variables

VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<public anon key>
Only the public anon key belongs in the front end. The service-role key must never be added to this project, to a build, or to source control.

Commands

npm install          # install dependencies
npm run dev          # local development server
npm run build        # production build into dist/
npm run preview      # preview the production build

Backend provisioning

  1. Create a Supabase project.
  2. Apply supabase/migrations/0001…0008 in order — schema, policies, reporting functions, triggers, storage bucket.
  3. Run the seed migration to create demo accounts and sample data, or create the first administrator profile manually (see §12).
  4. Set the two environment variables and rebuild.

13. Operating runbook

Onboard a food donor

  1. Donor registers and selects “Food donor”; the account activates immediately.
  2. They add a donation — it is created as pending and is not publicly visible.
  3. Administrator reviews it under Donations and approves; the donor is notified and it appears on /donations.

Fulfil a family request

  1. Beneficiary submits a request with urgency and household size.
  2. Administrator verifies the account if still pending, then approves the request under Requests.
  3. In Smart matching, pick the request, review the ranked candidates, create and confirm a match.
  4. Assign a volunteer; they are notified and the task appears in their board.
  5. Volunteer progresses the task to delivered; the donation, match and request close together and all three parties are notified.

Recover an unmatched donation

Cancel the match — the donation returns to approved and the request to approved, both available for a new pairing.
